## 2. High-Level Product Overview

Ayaw Kalimti is a personal, context-aware task application that attempts to surface a task when the user has a practical opportunity to act on it.

Conventional reminder applications commonly associate a task with one fixed time or one fixed location. Ayaw Kalimti instead allows a general Task to have multiple Opportunity Contexts. A Task may become eligible because of a Scheduled Reminder; arrival at or departure from a reusable Saved Place; arrival at a one-off Specific Destination; proximity to a useful Place Capability; or—after the MVP—a weather condition. A Deadline describes intended completion and Recurrence creates Task Occurrences; neither independently creates notification eligibility. Enabled Opportunity Contexts use flat OR semantics: any one matching Context may make the Task eligible. Completion state, snoozing, applicable cooldowns, deduplication, and Quiet Hours within their automatic-notification scope remain mandatory Hard Gates. Explicit Scheduled Reminders and Snooze reminders bypass Quiet Hours and the automatic cooldown.

The product’s distinguishing behavior is:

> Capture what needs to be done, retain it safely, and surface it once when the surrounding context makes action useful.

For example, “Buy medicine before Friday” may be associated with leaving Work, being near a pharmacy, and a Friday fallback schedule. Any one of these contexts may create an opportunity. If several match at once, the product sends one deduplicated notification and identifies the relevant reason rather than sending competing reminders.

Ayaw Kalimti is personal-first: its initial product owner is also its first daily user. It is nevertheless designed for eventual public use, with account isolation, bounded retention-controlled history, privacy controls, and a production-track architecture from the MVP onward.

The product MUST favor useful, explainable notifications over notification volume. It MUST NOT continuously track a user’s movement.

## 3. Formal Production Product Description and Requirements

### 3.1 Complete production product

The production version of Ayaw Kalimti is a public Android and iOS application for creating one-off and recurring personal tasks and associating them with one or more real-world opportunity contexts.

Users can capture tasks by typing or speaking. AI-assisted capture interprets the requested outcome, proposes relevant tools and contexts, and asks only the questions needed to make a vague task actionable. Relevant tools may include scheduling, recurrence, Saved Place or Specific Destination geofencing, Place Capability discovery, and weather evaluation. Confirmation is enabled by default. Users who prefer rapid or voice-first capture may enable automatic saving; automatically interpreted configurations remain visible and editable afterward.

Production users express location intent through three concepts: a reusable Saved Place, a Task-bound Specific Destination, or a Place Capability that describes anywhere the Task could be accomplished. Saved Places include Home, Work, School, and additional high-frequency locations and support arrival and departure Contexts. Specific Destinations cover exact addresses or map points such as pickup locations and event venues. Place Capabilities support compatible nearby discovery and may include individual-business preferences or exclusions. Provider categories remain internal mappings rather than the product's user-facing location model. The product may dynamically monitor a bounded set of relevant regions or use other privacy-preserving platform capabilities to recognize proximity opportunities without continuously tracking movement.

Production opportunity evaluation can consider Scheduled Reminders, Saved Place transitions, Specific Destination arrival, Place Capability matches, weather, Task state, Quiet Hours, snoozing, notification cooldowns, recent Evaluation Episodes, and prior feedback. Recurrence creates Task Occurrences, while Deadlines affect overdue state, urgency, and sorting. The user remains in control of the resulting Task and its Contexts.

The product provides actionable notification flows with authenticated per-Task Done, Snooze, and Not useful controls. It records enough history to prevent duplicates, apply fatigue rules, explain why a notification was sent, and measure whether contextual reminders are useful. It provides a configurable fallback digest because mobile operating systems and external notification providers cannot guarantee every background transition.

Production supports multiple user devices and synchronization. User data remains isolated by account. Users can inspect, correct, export, and delete their data. Location information is purpose-limited, minimized, protected, and never used for continuous movement tracking.

## 4. Product Foundations

### 4.1 Problem statement

People often remember a task when they cannot act and forget it when a useful opportunity appears. A time-only reminder can arrive when the user is busy or far from a relevant place. A fixed-location reminder requires the user to know and configure one exact location even when many places could satisfy the task. As reminders accumulate or repeat, users may begin ignoring them.

Ayaw Kalimti is intended to reduce missed, context-dependent tasks by retaining a general Task, observing only approved contextual signals, and producing a restrained notification when at least one useful opportunity context matches.

No external user research, market-size evidence, or quantitative validation has yet been approved. The product owner’s personal need is the initial evidence and validation context.

### 4.2 Intended users and usage context

The initial user is the product owner, using the application daily on Android. The eventual intended users are individuals who:

- Capture both one-off and recurring personal tasks.
- Forget tasks until an actionable time or place has passed.
- Want contextual assistance without continuous tracking.
- Prefer simple capture but may later customize how opportunities are recognized.
- Are willing to grant selected notification and location permissions when the benefit and data handling are clear.

No narrower demographic, medical, disability, workplace, or educational persona has been approved. The product MUST NOT claim to diagnose, treat, or compensate for a medical condition.

### 4.3 Product goals

| ID | Goal | Rationale | Evidence of progress | Scope |
|---|---|---|---|---|
| PG-001 | Enable a user to capture and manage general one-off and recurring Tasks with low friction. | Capture must be easier than relying on memory. | Users can successfully create, inspect, update, complete, and recur Tasks. | MVP and production |
| PG-002 | Surface unresolved Tasks when an approved opportunity context makes action useful. | Relevance is the central product value. | Contextual notifications are followed by Task actions and are explainable. | MVP and production |
| PG-003 | Protect attention by preventing duplicate, stale, or excessively repetitive notifications. | Notification fatigue would destroy trust and usefulness. | Duplicate suppression, cooldowns, snoozing, bundling, and Not useful feedback operate as specified. | MVP and production |
| PG-004 | Combine simple default behavior with increasing user control in production. | Customization must not make basic capture difficult. | MVP capture is structured and concise; production interpretation and advanced settings remain visible and editable. | MVP and production |
| PG-005 | Earn and preserve trust when processing sensitive Task and location information. | Users disclose Home, Work/School, routines, and intent. | Data is minimized, isolated, protected, deletable, and excluded from inappropriate telemetry. | MVP and production |

The personal MVP validation thresholds are defined in Section 6.5. They validate sustained usefulness for the product owner only; public-launch readiness requires later external validation and separately approved launch criteria.

## 5. Domain Model and Product Rules

### 5.1 Official domain vocabulary

| Term | Meaning and essential properties | Lifecycle and relationships |
|---|---|---|
| User | The owner of an isolated Ayaw Kalimti account and its data. | Owns Devices, Tasks, Saved Places, settings, and retained history. |
| Device | An authenticated mobile installation with permissions, local queue state, and a push-delivery address. | Belongs to one User; may become inactive or lose permissions. |
| Task | A general statement of work with status, optional Deadline, optional Recurrence, snooze state, and zero or more Opportunity Contexts. | One-off Tasks may become completed and remain reopenable for 30 elapsed days; recurring Tasks produce Task Occurrences; confirmed deletion is terminal; a Task with no enabled Context is Unscheduled. |
| Unscheduled Task | A Task with no enabled Opportunity Context. It appears in the Task list and may qualify for the fallback digest but does not independently create a contextual notification. | Becomes scheduled or contextual when the user adds an Opportunity Context. |
| Scheduled Reminder | A time-based Opportunity Context. A one-off reminder resolves its selected local date/time and creation timezone to one immutable instant; a selected time in a daylight-saving gap uses the first valid instant afterward, and a repeated time uses the earlier of the two valid instants. | Firing produces an Evaluation Event that may make its Task eligible; later timezone, daylight-saving, or manual-clock changes do not move the instant. |
| Deadline | The time by which the user intends the Task to be completed, resolved from selected local date/time and creation timezone to one immutable instant. A selected time in a daylight-saving gap uses the first valid instant afterward, and a repeated time uses the earlier of the two valid instants. It affects overdue state, urgency, and sorting but does not independently notify. | In the Task list, overdue Deadline-bearing items sort first by earliest Deadline, then future Deadline-bearing items by earliest Deadline, then no-Deadline items by oldest creation time; ties use creation time and canonical ID. May coexist with any Opportunity Context; notification at the Deadline requires a Scheduled Reminder at that instant. Later clock or timezone changes alter display, not the instant. |
| Recurrence | A current-device-local calendar rule that creates Task Occurrences daily, on selected weekdays, every N days, or every N weeks. It is not an Opportunity Context. | Remains active until edited, disabled, or deleted; each occurrence uses the Task’s enabled Contexts. Day/week intervals are calendar-based rather than fixed elapsed-hour durations. |
| Task occurrence | One actionable instance of a recurring Task. | Pending until completed; completion remains provisional during immediate Undo, then creates the next valid occurrence without completing the parent Task. |
| Completion Undo | The immediate lightweight reversal offered after completion. | Restores the same Task or occurrence identity without replaying historical Events or Notifications or restoring deleted history. Any still-valid automatic cooldown, Evaluation Episode deduplication, and Digest Acknowledgement remain effective. |
| Reopen | The authenticated action that returns the same completed one-off Task to Active while less than 30 elapsed days have passed since completion. | Does not recover a deleted Task or restore historical Events, Notifications, or deleted history. Any still-valid automatic cooldown, Evaluation Episode deduplication, and Digest Acknowledgement remain effective. |
| Opportunity Context | A user-visible condition that may independently make a Task eligible. Sibling Contexts use flat OR. | Belongs to a Task; may be enabled, edited, or removed. It is not a Deadline, Recurrence, Evaluation Event, or Hard Gate. |
| Flat OR eligibility | The rule that any one enabled Opportunity Context may make a Task eligible. | It does not bypass Hard Gates; each matching sibling Context remains independent. |
| Hard Gate | A mandatory delivery constraint applied after Context matching, including completion/deletion state, snooze, Quiet Hours, cooldown, and deduplication within their defined scopes. | Every applicable Hard Gate must permit delivery. |
| Quiet Hours | A user-configured current-device-local wall-time interval that suppresses automatic location, application-open, manual-check, and fallback-digest notifications. | A contextual match is recorded but not replayed when Quiet Hours end. Timezone, daylight-saving, or manual-clock boundary passage creates no Event or catch-up; explicit Scheduled Reminders and Snooze reminders bypass this gate. |
| Cooldown | An elapsed fatigue-control duration measured from authoritative notification submission. | Timezone, daylight-saving, and manual wall-clock changes do not shorten, extend, reset, or duplicate it. |
| Snooze | A Task action that selects an elapsed duration and creates a one-time Scheduled Reminder at the immutable due instant derived when the action is accepted. | Suppresses the Task until the due instant without removing its original Contexts; the reminder then bypasses Quiet Hours and the automatic cooldown if the Task remains unresolved. |
| Location Context Target | The user-facing intention of a location-based Opportunity Context. It is exactly one Saved Place, Specific Destination, or Place Capability. | Provider taxonomies are internal mappings, not additional target kinds. |
| Saved Place | A reusable meaningful location such as Home or Work/School. | Backed by an Anchor; may be selected for arrival or departure Contexts. |
| Anchor | The domain entity that backs a Saved Place and its monitored region. The MVP uses a fixed 300-metre region for Home and Work/School Anchors; it is not user-configurable but may be tuned during testing. MVP exact coordinates remain in protected device storage and the operating-system geofence service, never a server database or backup. | Produces Saved Place arrival or departure Evaluation Events when device support and permission allow. MVP cloud records use opaque identity without coordinates. Production may synchronize only end-to-end encrypted coordinate ciphertext whose keys the service never possesses. |
| Specific Destination | An exact address or map point attached to one Task rather than automatically saved for reuse. | MVP permits at most one per Task, arrival only, in a fixed 250-metre region; it may be captured by address search, map pin, or recognized map link. |
| Place Capability | A user-facing description of the kind of nearby place that could satisfy a Task. | Mapped internally to compatible provider types; MVP offers five approved shortcuts. |
| Applicable Place Capability Task | An Active one-off Task or current Pending Task Occurrence with at least one enabled Place Capability Context. | Notification Hard Gates do not remove it from evaluation; they are applied independently after a Context matches. Completed, deleted, non-current, and disabled work is not applicable. |
| Current-location Snapshot | A precise device-location reading requested for one permitted active Place Capability Evaluation Episode or one explicit Find Nearby interaction. | At most one is acquired per Episode or interaction. An Episode shares it transiently across applicable Task evaluations; Find Nearby uses it only for the selected Task and capability. It may be transmitted to the official place provider, directly or through in-memory service processing, but is never persisted in an app-controlled database, cache, durable queue, log, analytics system, crash report, or backup. Third-party handling is disclosed and governed by the provider review. |
| Effective Place Query | The complete provider-search inputs that determine whether Tasks can safely share one transient search result set. | In the MVP, the signature includes the Current-location Snapshot, Place Capability mapping, fixed radius, confirmed-open rule, and requested provider fields. Production additionally includes effective radius, business preferences or exclusions, and any other approved result-changing input. Task identity is not part of the signature. |
| MVP Place Match | The nearest confirmed-open provider result compatible with a selected Place Capability within one kilometre of the Current-location Snapshot. | Closed results, unknown opening status, and no results do not match and do not create an Opportunity. The MVP radius is fixed for users but tunable during testing. Production uses a global one-kilometre default with an advanced 250-metre-to-10-kilometre per-Place-Capability-Context override. |
| Find Nearby | A user action on one selected Task and Place Capability that requests one new Current-location Snapshot and performs one fresh transient search for the nearest currently usable result. | It is a separate non-Opportunity interaction: it does not create an Evaluation Event or Episode, wake other Tasks, create an Opportunity, or send a Notification. It displays the current result without retaining its business name, address, provider place identifier, or distance in cloud history or other app-controlled persistence. |
| Evaluation Event | A timestamped, idempotently identifiable observation such as a Saved Place transition, Specific Destination arrival, Scheduled Reminder firing, app-open check, or manual check. | May cause one or more Opportunity Evaluations; expires when too stale to act upon. It need not be one of the evaluated Task’s Contexts. |
| Opportunity Evaluation | The recorded evaluation of a Task for a particular Evaluation Event, including Context matches, Hard-Gate results, and the resulting Opportunity Outcome. | A Context match creates an Opportunity even if a Hard Gate suppresses Notification. |
| Opportunity | A detected chance to perform a Task because at least one Opportunity Context matched during an Evaluation Episode. | Exists independently of Notification delivery. |
| Opportunity Outcome | The result after freshness and Hard Gates, such as Deliverable, Suppressed Opportunity, or Expired Opportunity. | Remains distinct from Task lifecycle state and Notification State. |
| Notification State | The delivery lifecycle associated with a Notification, such as queued, submitted, or failed. | Remains distinct from Opportunity Outcome and Task lifecycle state; a Suppressed or Expired Opportunity has no submitted Notification. |
| Suppressed Opportunity | An Opportunity for which a Hard Gate prevented Notification submission. | Visible in Recent Activity; it is not a Notification. |
| Expired Opportunity | A directly evidenced Saved Place or Specific Destination Context match received too late for Notification eligibility. | Uses the original occurrence time, appears in Recent Activity and the Recent Opportunity Indicator within their 24-hour window, and never creates catch-up delivery. |
| Missed Evaluation | A permitted evaluation that could not determine a Context match, such as a stale Event for which a historical Place Capability search is prohibited. | May appear as diagnostic activity but is not an Opportunity and does not set the Recent Opportunity Indicator. |
| Recent Opportunity Indicator | A compact Task-list marker showing that an Opportunity was detected during the last 24 hours. | Does not distinguish Opportunity Outcome or Notification State; Missed Evaluation and Event Sync Failed alone do not set it. |
| Recent Activity | A user-visible 24-elapsed-hour history of Opportunities, Opportunity Outcomes, Notification States, Missed Evaluations, Event Sync Failed and other Retry Exhausted results, and user actions without exact coordinates. | Detailed status belongs here rather than in the Task list; entries use their original occurrence time rather than upload time. Underlying approved coordinate-free records may remain for no more than seven elapsed days. |
| Evaluation Episode | A logical wake-up boundary grouping duplicate or replayed Evaluation Events. MVP boundaries are one logical Saved Place transition, one Specific Destination arrival, one Scheduled Reminder firing, one eligible automatic foreground check, or one manual check; a place result inherits its initiating Episode. | Duplicate or replayed observations remain in the same Episode; a later independent wake-up creates another Episode. |
| Notification | A user-visible communication logically associated with one or more eligible Tasks. Its operating-system preview and protected in-app detail are distinct presentation surfaces. | Requested, queued, delivered to provider, opened, acted upon, failed, or expired; one same-Episode delivery envelope may retain independent associations with multiple Tasks. |
| Detailed Notification Preview | The MVP content shown by the operating system and carried through a third-party push provider. | Contains one Task-title/approved-reason row for a single Task; every row for a same-Episode group or digest of at most three Tasks; or exactly three rows and `+N more` above three. Only displayed rows, total or remaining count, opaque open routing, and necessary delivery/grouping metadata leave the protected application boundary. System-added precise destination and business details remain prohibited by PRIV-019. |
| Generic Notification Preview | An optional privacy-preserving production presentation that replaces semantic Task and reason content with neutral app copy and minimum non-semantic routing metadata. | Not an MVP capability; production customization remains FUT-017. |
| Authenticated Notification Detail | The protected in-app destination reached by tapping a Notification and resolving current Task and reason data after validating the product session and ownership. | Lists every authorized Task associated with the envelope, including preview overflow, and exposes applicable per-Task Done, Snooze, and Not useful controls; the routing reference grants no access by itself. |
| Notification action | A Task-scoped Done, Snooze, Not useful, or approved acknowledgement interaction performed inside the authenticated app. | Must be safe to repeat. Tapping or dismissing an MVP operating-system Notification is navigation or operating-system behavior, not a Task action. |
| Not useful | A Notification action meaning that the Task remains valid but the surfaced Opportunity was not useful. | Records feedback without changing the Task or its Contexts; another automatic Notification requires a new Evaluation Episode and expiry of the automatic cooldown. |
| Needs Attention | A visible synchronization result indicating that a queued instruction can no longer be applied as requested and needs a new user decision. | It is not an Opportunity, Notification, completion, or silent failure. An unresolved queued user action expires at 30 elapsed days, never applies afterward, and requires a newly issued action. |
| Retry Exhausted | The operational result after a deterministic bounded automatic retry policy ends without success. | It is not a Task state, Opportunity, Notification, acknowledgement, or completion and creates no inferred Task lifecycle change or error Notification. Replay remains bounded by the seven-day Event or 30-day action lifetime. |
| Retention Clock | The elapsed lifetime measured from a record's canonical occurrence or creation time. | Upload, replay, retry, state refresh, aggregation, timezone change, and wall-clock change do not restart it. |
| Event Sync Failed | The Retry Exhausted result for a queued Evaluation Event that did not reach authoritative processing. | It creates no Opportunity or Recent Opportunity Indicator and preserves original occurrence time and idempotency identity only through the Event's seven-day retention deadline; safe replay also follows ordinary freshness rules. |
| Degraded Capability | A persistent in-app health state for a provider, queue, permission, or required device capability that is not currently operating reliably. | Remains visible until verified recovery even after related Recent Activity ages out. |
| Fallback digest | A configurable daily summary of qualifying unresolved Tasks sent independently of successful geofence detection. It is not an Opportunity and does not set the Recent Opportunity Indicator. | Identifies itself as a digest and shows at most three Task-title/non-Opportunity-reason rows plus `+N more`; tapping opens the complete authenticated list. It respects Quiet Hours and cooldown, and runs at most once per local calendar day. |
| Digest Acknowledgement | A recorded interaction showing awareness of a specific Task after the preceding digest. | Opening the Task from Recent Activity, opening that specific Task from a digest's authenticated list, or applying Done, Snooze, or Not useful counts for that Task only. Opening Task details directly from the Task list or merely opening the digest's multi-Task list acknowledges no Task. |

“Opportunity Context,” “Evaluation Event,” and “Evaluation Episode” MUST NOT be used interchangeably. A Context is configured intent; an Event invokes evaluation; an Episode groups duplicate or replayed Events from one logical wake-up.

### 5.2 Task and occurrence states

| Entity | Valid state | Meaning | Allowed transitions |
|---|---|---|---|
| One-off Task | Active | Unresolved and eligible subject to rules. | Active → Completed; Active → Deleted |
| One-off Task | Completed | User marked the work complete. | Immediate Completion Undo; Completed → Active through Reopen while `now < completed_at + 30 elapsed days`; Completed → Deleted |
| Recurring Task | Active | Recurrence definition remains enabled. | Active → Deleted; recurrence configuration may be edited |
| Task occurrence | Pending | Current recurrence is unresolved. | Pending → Completed |
| Task occurrence | Completed, provisional | User completed this recurrence while immediate Undo remains available. | Undo → Pending; closing Undo materializes the next occurrence and commits completion |
| Task occurrence | Completed, committed | Its successor occurrence exists. | No Reopen or Undo; future work follows the recurrence definition |
| Any Task | Deleted | Explicitly confirmed, no longer visible or eligible, and unrecoverable through the product or backups. | Terminal |

Snoozing is not a Task lifecycle state. It is a temporary eligibility constraint. Not useful is feedback and temporary suppression; it is not completion and does not mutate Contexts.

### 5.3 Core product rules

| ID | Rule |
|---|---|
| RULE-001 | A Task MUST have a non-empty user-visible title. A Task with no enabled Opportunity Context is Unscheduled and cannot independently produce a contextual notification. |
| RULE-002 | Enabled Opportunity Contexts are sibling conditions evaluated using flat OR: one matching Context is sufficient to detect an Opportunity. For example, Leaving Work may match even when a separate Near Pharmacy Context does not. |
| RULE-003 | Completion, deletion, snooze, Quiet Hours, applicable cooldown, and duplicate constraints MUST be evaluated independently per Task after OR Context matching and before any notification grouping. They suppress delivery only within their defined scopes and never inherit from another grouped Task. |
| RULE-004 | If multiple Contexts match one Task during one Evaluation Episode, they MUST be consolidated into one per-Task eligibility decision. After every Task is evaluated independently, all Deliverable candidates from that Episode MUST share one Notification delivery envelope; Suppressed or Expired candidates and candidates from another Episode MUST NOT join it. |
| RULE-005 | A Deadline is optional and does not independently create eligibility. A Deadline and a one-off Scheduled Reminder each resolve the selected local date/time and creation timezone to an immutable instant. A selected local time in a daylight-saving gap resolves to the first valid instant afterward; a repeated time uses the earlier of the two valid instants. Notification at the Deadline requires a Scheduled Reminder configured for that instant; later timezone, daylight-saving, or manual-clock changes do not move either fixed instant. |
| RULE-006 | Recurrence creates Task Occurrences but is not an Opportunity Context. Daily, selected-weekday, every-N-day, and every-N-week rules use current-device-local calendar dates and wall time rather than fixed 24- or 168-hour durations. Completing a recurring occurrence MUST preserve the Recurrence definition and remain provisional while immediate Undo is available; the successor MUST NOT be created until that affordance closes. Undo before successor creation restores the same occurrence; afterward completion is committed and cannot reopen. Completion Undo and one-off Reopen preserve every still-valid automatic cooldown, Evaluation Episode deduplication record, and Digest Acknowledgement; neither restores an expired or deleted historical record. |
| RULE-007 | Not useful means the Task remains valid but the surfaced Opportunity was not useful. It MUST record matched Context reasons, preserve Task configuration, and require both a new Evaluation Episode and expiry of the automatic cooldown before another automatic notification. |
| RULE-008 | An Evaluation Event received more than once with the same idempotency identity MUST NOT create additional authoritative effects. |
| RULE-009 | A location Evaluation Event processed more than 15 minutes after its recorded occurrence MUST NOT produce a Notification or historical Place Capability lookup. Directly evidenced Saved Place or Specific Destination matches follow RULE-032; unevaluated Place Capability checks follow RULE-033. |
| RULE-010 | A permitted, sufficiently recent Saved Place transition or Specific Destination arrival MUST wake Place Capability evaluation for every Applicable Place Capability Task, even when the triggering target or transition is not a Context on that Task. An eligible automatic app-foreground check and a user-initiated manual check do the same. The triggering Event directly satisfies only Contexts that actually match it. Scheduled Reminders, Recurrence, Deadlines, digest runs, cooldown expiry, and passage of time alone MUST NOT initiate a Place Capability evaluation. Find Nearby is a separate explicit lookup for one selected Task and MUST NOT create an Evaluation Event, Episode, Opportunity, or global fan-out. |
| RULE-011 | The fallback digest MAY surface qualifying unresolved Tasks even when no contextual event was successfully observed, but it MUST identify itself as a digest rather than a detected Opportunity and MUST NOT set the Recent Opportunity Indicator. Each displayed digest row uses a concise non-Opportunity reason indicating that the Task remains unresolved; exact copy is a design detail. Tapping the digest opens its authenticated list and acknowledges no Task; subsequently opening one Task from that list acknowledges only that Task. It respects Quiet Hours and the automatic cooldown, and a run suppressed by Quiet Hours is not replayed later. |
| RULE-012 | A dependency failure MUST leave current authoritative Task state unchanged and MUST NOT infer delivery, acknowledgement, action, or completion. A still-active unresolved Task remains unresolved. Retry Exhausted sends no error Notification and remains visible in the app through its appropriate failure result or Degraded Capability state. |
| RULE-013 | Snooze selects an elapsed duration and creates a one-time Scheduled Reminder at the immutable due instant derived when Snooze is accepted. At expiry, an unresolved Task may notify even if the original location Context is no longer true; the original Contexts remain unchanged. Timezone, daylight-saving, and manual wall-clock changes do not shorten, extend, or duplicate it. The explicit reminder bypasses Quiet Hours and the automatic cooldown. |
| RULE-014 | A detected Opportunity MUST remain distinguishable from its Opportunity Outcome and Notification State. A Suppressed Opportunity is not a Notification. Grouping merges only presentation and delivery: each included Task retains its own Opportunity, Outcome, Notification association, cooldown, digest accounting, and action targets. |
| RULE-015 | The Task list shows only a compact Recent Opportunity Indicator for Opportunities detected in the last 24 hours. Detailed Outcomes and actions belong in Recent Activity. |
| RULE-016 | An automatic contextual Opportunity detected during Quiet Hours MUST be recorded as a Suppressed Opportunity and MUST NOT be delivered later merely because Quiet Hours ended. A later independent Evaluation Episode may notify if every applicable Hard Gate permits it. |
| RULE-017 | At a digest run, eligibility is calculated independently per Task. A Task qualifies only when active and unresolved and when it has had neither an intervening successful Notification submission nor a Digest Acknowledgement after the preceding digest. A successful grouped submission counts for each included Task; a final failed grouped delivery leaves every included Task's Notification State failed and does not count as successful submission. Completed, deleted, actively snoozed, future-occurrence, and future-only Scheduled Reminder Tasks are excluded. Unscheduled Tasks, Tasks with unacknowledged Suppressed or Expired Opportunity Outcomes, Tasks with a final failed Notification State, and Tasks with Missed Evaluations or Event Sync Failed may qualify. Opening Task details directly from the Task list or opening the digest's multi-Task list is not a Digest Acknowledgement; opening one specific Task from that digest list acknowledges only that Task. |
| RULE-018 | MVP onboarding suggests an 8:00 PM digest time in the device's current local timezone and requires confirmation or change. The selected time MUST be outside current Quiet Hours. A later conflict MUST be shown rather than silently moving the time. The digest follows current-device-local time and runs at most once per local calendar day. A timezone change or forward manual-clock jump that crosses its time skips that day's run rather than catching up; a daylight-saving gap uses the first valid instant afterward, and a repeated local time runs once at the earlier of its two valid instants. A backward clock change never duplicates a run. |
| RULE-019 | Both MVP Saved Place slots are optional. Zero or one Home and zero or one Work/School Saved Place may exist, each backed by an Anchor with a fixed 300-metre MVP region. The radius is not user-configurable but may be tuned during testing; absence of Saved Places or location permission MUST NOT disable non-location product behavior. |
| RULE-020 | MVP exact Anchor and Specific Destination coordinates MUST remain only in protected device storage and the operating-system geofence service. Server records and transition Events use opaque location-target identity and MUST NOT contain raw coordinates. At most one Current-location Snapshot may exist transiently for one permitted Place Capability Evaluation Episode or explicit Find Nearby interaction and MUST NOT be persisted. |
| RULE-021 | An MVP Place Capability Context matches only when the nearest compatible result is confirmed open and within one kilometre. Closed results, unknown opening status, or no result MUST NOT create an Opportunity. The MVP user cannot change the radius; production users can. |
| RULE-022 | Production precise-location synchronization may persist only end-to-end encrypted coordinate ciphertext. The service MUST possess neither plaintext nor a decryption key; adding a device requires an existing-device approval or user-held recovery key, otherwise precise targets must be re-entered. |
| RULE-023 | Cloud Place Capability history, authenticated in-app reasons, and a Detailed Notification Preview MAY identify the matched capability and Opportunity Outcome, but MUST NOT add business identity, address, provider place identifier, or distance. Within-Episode result sharing follows RULE-038. Find Nearby MUST perform a fresh transient search and MUST NOT reuse or persist a result from an earlier Episode or interaction. |
| RULE-024 | Every location-based Opportunity Context targets exactly one Saved Place, Specific Destination, or Place Capability. Provider taxonomies MUST remain internal mappings and MUST NOT become the user-facing location ontology. |
| RULE-025 | An MVP Task may contain no more than one Specific Destination. It supports arrival only, uses a fixed 250-metre region, and MUST NOT automatically become a Saved Place or Anchor. |
| RULE-026 | MVP Specific Destination capture supports address search, map-pin selection, and recognized map links. The MVP MUST NOT scrape arbitrary pages or search private listing content; an unresolved link requires the user to select or confirm a point manually. |
| RULE-027 | The Android MVP may monitor at most 20 active Specific Destinations per device. The limit governs simultaneous monitoring rather than retention and is testing-tunable but not user-configurable. Reaching it MUST NOT silently evict a region; the affected Context remains disabled until capacity is freed, while the Task may still be saved with other Contexts. |
| RULE-028 | An MVP Specific Destination is registered while its one-off Task is Active or its recurring Task remains enabled. It is unregistered when the one-off Task is completed or deleted, the Context is removed or replaced, or the user logs out or deletes the account. Undoing completion or reopening a completed one-off Task attempts to re-register its region under current permission, capability, and capacity rules; failure leaves the Context visibly disabled without evicting another region. A recurring Task retains its region while enabled. |
| RULE-029 | Entering a Specific Destination from outside creates one Evaluation Episode. Duplicate callbacks, remaining inside after cooldown expiry, and app restart while still inside do not create another Episode. A confirmed exit rearms the destination; a later re-entry creates another Opportunity. During cooldown, that Opportunity is Suppressed and no Notification is created or caught up when cooldown expires. |
| RULE-030 | MVP Task details may show the user-confirmed Specific Destination label, any available address, and a map from protected local data. The original capture query or link is discarded. Cloud history and authenticated Recent Activity retain only that a Specific Destination arrival occurred, without the destination label, address, venue, map link, or coordinates. A Detailed Notification Preview may include the user-authored Task title and a generic Specific Destination arrival reason, but the product MUST NOT add the destination label, address, venue, map link, or coordinates. Production synchronization may carry the precise details only as end-to-end encrypted ciphertext. |
| RULE-031 | A queued location Event is fresh for notification eligibility only when the server processes it no more than 15 minutes after its recorded occurrence time. The server evaluates age from the Event occurrence rather than treating reconnection as a new transition. |
| RULE-032 | A Saved Place or Specific Destination Event older than 15 minutes MUST NOT produce a Notification. When the transition itself directly proves a configured Context matched and its occurrence remains within the 24-hour activity window, the product records an Expired Opportunity, sets the Recent Opportunity Indicator, and shows the original occurrence time in Recent Activity. |
| RULE-033 | A stale location Event MUST NOT trigger a historical Place Capability search. If no other Context match is directly evidenced, it creates a Missed Evaluation entry rather than an Opportunity and does not set the Recent Opportunity Indicator. The 15-minute rule does not expire queued notification actions. |
| RULE-034 | A valid product session refreshes without arbitrary periodic reauthentication. Explicit logout clears the product session, protected local precise targets and destination display data, registered geofences, and durable queues. Account deletion always requires a fresh Google authentication flow. |
| RULE-035 | An offline Done action remains queued until it is idempotently applied, becomes inapplicable, or reaches 30 elapsed days from its original action time. Not useful may affect only its original Opportunity. Snooze applies only when its derived due instant remains in the future at replay; otherwise it becomes a visible Needs Attention result and MUST NOT create an immediate stale reminder. If automatic retries exhaust first, a still-applicable action remains durable and manually retryable with the same idempotency identity only before its 30-day deadline. At that deadline it expires without mutation; the queued instruction and associated recovery entry are removed, and any continuing intent requires a newly issued action. Retry does not extend the deadline. |
| RULE-036 | Confirmed account deletion immediately revokes product access and clears local sensitive state, completes deletion from active app-controlled cloud systems within 24 hours, expires affected app-controlled encrypted backups within 30 days, and cannot be undone. It does not delete the user's Google account. |
| RULE-037 | The MVP MUST start no more than one automatic app-foreground Place Capability Evaluation Episode in any rolling 15-minute window, and only when at least one Applicable Place Capability Task exists. The window starts when the automatic attempt begins, regardless of its eventual location or provider outcome. A user-initiated manual check and an otherwise-permitted Saved Place transition or Specific Destination arrival evaluation bypass and neither start, extend, nor reset this foreground window. The throttle does not create a catch-up evaluation when its window expires and is distinct from the per-Task notification cooldown. |
| RULE-038 | One Place Capability Evaluation Episode MUST acquire at most one Current-location Snapshot and perform at most one provider search per distinct Effective Place Query. The Snapshot and result set are shared only in transient memory across Applicable Place Capability Tasks in that Episode, while each Task's Context matching, Hard Gates, Outcome, and deduplication remain independent. The data is discarded when the Episode finishes and MUST NOT be persisted or reused by a later Episode. |
| RULE-039 | Every MVP push-provider payload and operating-system Notification preview MUST use a Detailed Notification Preview. Each displayed row contains the user-authored Task title and one concise approved reason. A contextual reason MAY identify a Scheduled Reminder or Snooze, Saved Place name and transition, generic Specific Destination arrival, or matched Place Capability; a digest row uses a concise non-Opportunity reason indicating that the Task remains unresolved. A single-Task preview has one row. A same-Episode group or digest shows every row at a total of three or fewer, or exactly three rows plus `+N more` above three. Deadline-bearing Tasks sort by Deadline timestamp ascending; no-Deadline Tasks follow by `Task.created_at` ascending; equal Deadline timestamps use `Task.created_at` ascending and canonical `Task.id` ascending, while equal no-Deadline creation times use canonical `Task.id` ascending. Once selected, rows and order are frozen for the envelope and every retry. Only displayed rows, total or remaining count, an opaque open-routing reference, and necessary delivery and grouping metadata enter the external payload; undisplayed titles, reasons, identifiers, and full membership remain server-side. One Episode MUST NOT be split. The title may itself contain sensitive information and this exposure MUST be disclosed, but the product MUST NOT add raw coordinates, an exact address, a Specific Destination label or venue, map link, business identity, provider place identifier, or distance. The MVP operating-system surface exposes no app-defined Done, Snooze, or Not useful control: body tap only opens Authenticated Notification Detail and dismissal invokes no app-defined Task action. Opening a digest list acknowledges no Task; opening one Task from that list acknowledges only that Task. |
| RULE-040 | Retry Exhausted MUST create no error Notification and no inferred Task transition. Exhausted pre-match place evaluation becomes a Missed Evaluation; exhausted post-match push submission leaves Notification State failed; an exhausted queued Evaluation Event becomes Event Sync Failed and remains replayable only inside its seven-day record lifetime and ordinary freshness limits; an exhausted still-applicable queued user action becomes Needs Attention only through its 30-day action lifetime; and the affected capability remains Degraded until verified recovery. A later genuine Event evaluates normally, digest eligibility follows RULE-017, and a manual context check starts a fresh Episode and Snapshot rather than treating stale location evidence as current. |
| RULE-041 | Recent Activity and its indicator use original occurrence time and remain visible for 24 elapsed hours. Coordinate-free Events, evaluations, Notification records, feedback, sensitive derived-history records, and sanitized operational logs MUST be deleted from active app-controlled systems no later than seven elapsed days after canonical occurrence or creation. Upload, replay, retry, state refresh, timezone change, and wall-clock change MUST NOT restart retention. Active Task/Context configuration, current lifecycle state, recurrence settings, fixed reminder/Deadline instants and creation timezone, Quiet Hours, and current capability health are not derived history. A transport-queue entry is settled only when applied, deduplicated, cancelled, rendered inapplicable, or terminally expired with no authorized replay remaining; the entire entry MUST be deleted within 24 elapsed hours after settlement and no later than the underlying record deadline, including immediate deletion when settlement occurs at that deadline. Any separate authoritative record follows its own retention rule. Unresolved Evaluation Events cannot outlive seven days; unresolved user actions and recovery entries cannot outlive 30 days. Every encrypted backup MUST expire within 30 days, and restore processing MUST reapply every deletion and retention cutoff without resurrecting expired or deleted data. |
| RULE-042 | Recurrence and Quiet Hours use current-device-local calendar and wall time. One-off Scheduled Reminders and Deadlines preserve immutable instants resolved using the creation timezone. Cooldown, Snooze, retention, and recovery windows use elapsed time. A nonexistent selected or recurring local time resolves to the first valid instant after a daylight-saving gap; a repeated selected or recurring time uses the earlier valid instant, and a repeated digest time runs at the earlier valid instant. A forward manual-clock jump skips every crossed recurrence or digest slot without catch-up; a backward change never duplicates one. Logical identities prevent timezone, daylight-saving, and manual-clock changes from duplicating an occurrence, Event, Notification, completion, retention window, or recovery window. |
| RULE-043 | The MVP Task list orders displayed actionable items with overdue Deadlines first, then future Deadlines, then items without a Deadline. The first two groups sort by Deadline timestamp ascending; the final group sorts by `Task.created_at` ascending. Equal Deadline timestamps sort by `Task.created_at` ascending and then canonical `Task.id` ascending; equal no-Deadline creation times sort by canonical `Task.id` ascending. |

### 5.4 Key product journeys

#### Journey J-001: Create a multi-context Task

1. An authenticated user enters a Task title.
2. The user selects two or more supported Contexts.
3. The product displays the resulting configuration.
4. The user saves it.
5. The Task becomes Active with every selected Context retained.

Related requirements: FR-001, FR-003, FR-004, FR-101, FR-105, FR-106.

#### Journey J-002: Receive a location opportunity

1. A permitted Saved Place transition, Specific Destination arrival, eligible foreground check, or manual check creates one Evaluation Episode.
2. The Event is durably identified, and directly matching location Contexts remain Task-specific.
3. The Episode fans out to every Applicable Place Capability Task.
4. The product acquires one Current-location Snapshot, groups Tasks by Effective Place Query, and performs at most one transient provider search per group.
5. Each Task's Context match, Hard Gates, Outcome, and duplicate rules are evaluated independently.
6. The Snapshot and provider results are discarded when Episode processing finishes.
7. All Deliverable candidates from the Episode share one explainable Notification envelope; each Task retains independent state and controls.

Related requirements: FR-015 through FR-018, FR-118 through FR-132, FR-175 through FR-178.

#### Journey J-003: Complete a recurring occurrence

1. A recurring Task becomes eligible.
2. The user selects Done.
3. The current occurrence becomes provisionally Completed while the immediate Undo affordance remains available; no successor yet exists.
4. Undo restores the same occurrence to Pending, or closure of that affordance commits completion exactly once. Persistence of the affordance across process exit is not required by the MVP.
5. The parent recurrence remains active and creates exactly one next occurrence under its current-local daily, weekday, N-day, or N-week rule.
6. Once that successor exists, the prior occurrence cannot be reopened.

Related requirements: FR-002, FR-020, FR-111 through FR-117, FR-129, FR-134.

#### Journey J-004: Recover from offline operation

1. An Evaluation Event or notification action occurs without network access.
2. The device stores it in a retention-bounded durable local queue.
3. The device later reconnects and submits it with the same idempotency identity.
4. The server applies the effect once, rejects it as stale or inapplicable, or expires it at the applicable seven-day Event or 30-day action deadline.
5. A transport-queue entry is settled only when no authorized replay remains and is deleted within 24 hours after settlement and no later than its underlying deadline; settlement at that deadline deletes it immediately. A separate authoritative coordinate-free record follows its own seven-day limit.

Related requirements: FR-143 through FR-145, FR-150, FR-178, FR-179; PI-006.

#### Journey J-005: Recover contextual permissions

1. The user revokes a required location or notification permission.
2. The app displays the affected capability as degraded.
3. Time-based functionality that does not require the missing permission remains available.
4. The user receives actionable instructions to restore the capability.

Related requirements: FR-025, FR-146, FR-147, FR-178; PI-008.

#### Journey J-006: Delete the account

1. An authenticated user requests account deletion.
2. The product explains the effect and requests deliberate confirmation.
3. The product removes or irreversibly schedules removal of associated cloud data.
4. The user receives an observable result.
5. Any disclosed legal or operational retention exception is documented.

Related requirements: FR-028, FR-148; PI-009.

## 6. MVP Product Description and Requirements

### 6.1 MVP product description

The MVP is an Android 11/API 30-and-newer, account-backed version of Ayaw Kalimti built in the production repository and on the production-track domain model. It does not claim iOS support.

It validates whether users benefit from general Tasks that can be associated with multiple OR opportunity contexts. Capture is structured and does not use AI. Users can manage one-off and recurring Tasks and use Scheduled Reminder, Saved Place, Specific Destination, and Place Capability Contexts. The two optional Saved Place slots are Home and one Work/School; both support arrival and departure. Each Task may instead or additionally use one arrival-only Specific Destination selected by address search, map pin, or recognized map link. Place Capability matching is limited to grocery/supermarket, pharmacy, bank/ATM, convenience store, and mall.

The MVP does not continuously track location and does not independently wake merely because the user passes a compatible business. Specific Destination arrival uses a bounded task-specific region. Each sufficiently recent Saved Place transition or Specific Destination arrival, eligible application-open check, and manual context check evaluates every Applicable Place Capability Task. One transient location Snapshot and one provider search/result set per distinct Effective Place Query are shared within that Episode and then discarded.

Eligible Tasks produce detailed push Notifications. A single-Task preview shows the user-authored Task title and a concise reason. All Deliverable candidates from one Evaluation Episode share one Notification envelope. Same-Episode and digest previews show up to three Task-title/reason rows and `+N more` when needed; tapping opens the complete authenticated list. The MVP operating-system surface is tap-to-open only, while authenticated detail provides per-Task Done, Snooze, and Not useful controls. Hard suppression rules, per-Task deduplication, and a configurable daily fallback digest protect against missed Events and notification fatigue. Evaluation Events and notification actions are durably queued while offline within their approved retention limits. General offline Task creation or editing is not required.

The MVP requires a Google-authenticated account and isolates every user’s data. The production-MVP environment is personal validation and permits product access only to the product owner's configured identity; isolated development and preview environments use controlled test accounts for authorization and compatibility verification. MVP use and each permitted test account assume one active Android installation at a time, but the release matrix exercises separate physical devices across the supported Android range. The product neither builds nor enforces a device-transfer workflow. Coordinated multi-device behavior and synchronization guarantees remain production work. Account deletion and deletion of Saved Places, Specific Destinations, and retained location history are included.

### 6.2 MVP scope

#### Included

- Android mobile application supporting Android 11/API 30 and newer.
- Required authenticated account.
- Sign in with Google through OAuth 2.0/OpenID Connect using Authorization Code with PKCE and minimum identity scopes.
- Server-enforced production-MVP access limited to the configured product-owner identity, with controlled test accounts confined to isolated development and preview environments.
- General one-off and recurring Tasks.
- Structured Task capture without AI.
- Multiple opportunity Contexts per Task using flat OR eligibility.
- Optional deadline.
- Recurrence: daily, selected weekdays, every N days, and every N weeks using the current-device local calendar and wall time.
- One-off Scheduled Reminders and Deadlines preserve the immutable instant selected in their creation timezone; cooldown and Snooze use elapsed durations; Quiet Hours use current-device local wall time.
- Immediate completion Undo, a minimal authenticated Recently Completed section for one-off Reopen during its 30-day window, and explicitly confirmed irreversible Task deletion.
- A maximum of one Home Saved Place and one Work-or-School Saved Place, each backed by an Anchor.
- Arrival and departure Contexts for each configured Saved Place.
- At most one arrival-only Specific Destination per Task, using a fixed 250-metre region.
- Specific Destination capture by address search, map pin, or recognized map link, with manual point selection when a link cannot be resolved.
- At most 20 simultaneously monitored Specific Destinations per device, with visible capacity handling, immediate cleanup when an eligible one-off Task ends, and ordinary re-registration attempts when a completed one-off Task is reopened.
- Five approved Place Capability shortcuts.
- Global evaluation of every Applicable Place Capability Task after a sufficiently recent Saved Place transition or Specific Destination arrival, eligible application opening, or manual check, using one transient Snapshot and one search/result set per distinct Effective Place Query in that Episode.
- Time and recurrence evaluation.
- Quiet hours, snoozing, cooldown, and duplicate suppression.
- Detailed Notification previews with mandatory same-Episode grouping, at most three displayed Task rows plus `+N more`, tap-to-open-only operating-system behavior, and complete authenticated per-Task detail and actions.
- Configurable daily fallback digest.
- Retention-bounded durable offline queuing for Evaluation Events and notification actions.
- Permission and configuration health.
- Account, Saved Place, Specific Destination, and retained location-history deletion.

#### Explicitly excluded

- iOS.
- AI parsing, clarification, and automatic saving.
- Voice-first capture.
- More than two Saved Place slots.
- Independent business-proximity wakeups or dynamic business geofences.
- Arbitrary-page scraping or private-listing search for destination extraction.
- Business preferences or exclusions.
- Weather.
- Route-detour calculations.
- Cross-device synchronization guarantees.
- Device-transfer or multi-device-management UI.
- Full offline Task creation or editing.
- Collaboration.
- Calendar-provider access and personal-message inbox access. A future explicit share-to-app capture path is also outside the MVP.
- Arbitrary or nested Boolean rule-builder UI.
- Automatic Task completion.
- Microservices, n8n, Telegram, Tasker, or phone Shortcuts as the production application.

### 6.4 MVP completion definition

The MVP qualifies as complete only when:

1. Every Must requirement in FR-101 through FR-180 has a passing acceptance criterion or an explicitly approved, documented exception.
2. All MVP-blocking Open Decisions referenced by a requirement have been resolved.
3. Required privacy, security, deletion, authorization, offline replay, and failure-recovery tests pass.
4. Core behavior is verified on physical devices at the oldest supported and current Android versions using a development or release build capable of background geofencing.
5. The MVP does not contain an excluded capability presented as complete.
6. Known platform limitations and degraded permission states are visible to the user.
7. The implementation has passed a requirement-by-requirement alignment audit.

### 6.5 Personal MVP validation gate

The completed MVP validates the personal product hypothesis only when all of the following are true during one four-consecutive-week validation period:

1. The product owner voluntarily uses the app on at least five distinct days in each of the four weeks.
2. The owner creates or actively manages at least 30 real Tasks, of which at least 10 use a location-based Opportunity Context or combine two or more Opportunity Contexts.
3. At least 70 percent of contextual reminder instances are judged useful, and no more than 20 percent receive Not useful feedback. One instance means one Task association in a submitted contextual Opportunity Notification, including each Task in a grouped envelope but excluding a Fallback Digest. Every such instance in the period is included, and the gate cannot pass if none occurs.
4. Controlled tests produce zero duplicate Notifications for the same Task and Evaluation Episode.
5. No critical privacy, security, account-isolation, deletion, or data-loss defect remains unresolved.
6. At the end of the period, the owner chooses to continue using the app without requiring a fundamental product or architecture rebuild.

Counting rules make the gate reproducible without adding an analytics dependency:

- The owner records a start date and validation timezone. The period begins at 00:00 on that local date and consists of four adjacent seven-local-calendar-day blocks; travel does not change the tally timezone.
- A use-day contains at least one intentional foreground Task interaction: creating or viewing a Task, editing it, using a Task action, opening it from a Notification or digest, or starting a manual Context check. Background evaluation, passive Notification receipt, and an automatic digest run do not count by themselves.
- The 30-Task threshold counts distinct canonical Task identities created or actively managed during the period. Edit, Done, Undo, Reopen, Snooze, and Not useful are qualifying management actions; viewing, opening, passive receipt, and a manual Context check alone do not qualify. Seeded, demo, and controlled-test fixtures are excluded, and all occurrences of one recurring Task count as one Task. The 10-Task subset uses at least one location-based Context or at least two enabled Opportunity Contexts during the period.
- Each contextual reminder instance receives one final tally classification: Useful, Not useful, or Unjudged/other. The Not useful action classifies that Task instance as Not useful; the owner records Useful judgments manually. Every instance remains in the percentage denominator, while Unjudged/other contributes to neither numerator.
- The owner keeps a defect log. A defect is Critical for this gate when it causes or presents a credible path to unauthorized Task or precise-location disclosure, cross-account access, irreversible unintended Task/account data loss, or failure to honor confirmed deletion. A resolved and regression-tested defect is not unresolved.
- Continued use is a dated yes/no owner attestation. A fundamental rebuild means replacing the canonical Task/Context/Opportunity model, abandoning the production-track repository, or requiring wholesale replacement of the approved production-track architecture or its primary mobile/backend boundaries before continued daily use. Ordinary bug fixes, user-interface refinements, tuning, dependency upgrades, bounded migrations, and internal refactoring do not count.

To claim the gate has passed, the owner MUST maintain the tally, defect log, controlled-test results, and attestation in a user-controlled private record outside Ayaw Kalimti's app-controlled storage. This evidence requirement does not authorize product analytics in the MVP or four-week per-instance product retention; any later optional production analytics remain low priority and follow PRIV-010 and PRIV-020. Ordinary in-product records still follow their approved retention limits. Passing validates only a personal-first MVP. It does not authorize public release, which requires external validation and separately approved production launch criteria.

### 8.6 Failure behavior

| Condition | Required product behavior | User intervention |
|---|---|---|
| Duplicate Evaluation Event | Apply its authoritative effect at most once. | None |
| Delayed or out-of-order location Event | Reconcile idempotently. Through 15 minutes, evaluate against current Task state; afterward, never notify, record a directly evidenced Expired Opportunity when applicable, and never perform a historical Place Capability search. | Inspect Recent Activity or capability health |
| No mobile network | Queue Evaluation Events and notification actions durably within their seven-day and 30-day lifetimes. After bounded retries exhaust, record Event Sync Failed or Needs Attention without an error Notification; terminal expiry performs no Task effect and deletes the transport and recovery entries at the underlying deadline. | Reconnect; inspect in-app status; safely retry before expiry or issue a new action afterward |
| Place provider returns no usable result | Leave Tasks using that Effective Place Query unresolved and do not invent a place or Opportunity. | Use Find Nearby, retry manually, or wait for a later Event |
| Place provider unavailable | Retry within the bounded policy while independent queries continue when possible. On exhaustion, record a Missed Evaluation, show the Degraded Capability in-app, and send no error Notification. | Retry manually with a fresh Episode or wait for a later Event |
| Push provider unavailable | Retain the outbox/delivery state for bounded automatic retry and do not claim user delivery. On exhaustion, retain Notification failed in-app and do not send or manually resend an error or stale push. | Normally none; later genuine Events and digest remain eligible under ordinary rules |
| Database unavailable | Reject or retry safely without acknowledging a state change that was not committed; show degraded service if the failure prevents a user action or workflow from completing. | Retry only when the app identifies a safe user action; otherwise wait for service recovery |
| Permission revoked or service disabled | Mark relevant capability degraded and retain unrelated Task functionality. | Follow recovery guidance |
| App process restarts | Preserve applicable unacknowledged local queues, reconstruct device health, and purge entries whose canonical retention deadline has passed. | None |
| Invalid input | Reject atomically with actionable validation; do not partially create configuration. | Correct the input |
| Logout or deletion with queued work | Prevent queue upload to another account and prevent deleted state resurrection. | None |

Location Event freshness is defined by OD-041 and queued-action conflict behavior by OD-011. Retry counts and backoff remain operational configuration, but the deterministic Retry Exhausted product behavior is defined by OD-018, RULE-040, and REL-014.

## Appendix A. Specification Governance

### A.1 Change-control process

1. A proposed change identifies every affected requirement, invariant, security requirement, and acceptance-criterion ID.
2. It explains which Product Goals the change supports.
3. It identifies conflicts with Product Invariants and Non-Goals.
4. It classifies itself as a clarification, correction, implementation change, or product change.
5. It includes new or updated acceptance criteria where observable behavior changes.
6. It identifies scope, privacy, security, data, reliability, migration, and external-dependency effects.
7. It does not silently rewrite historical decisions.
8. Approved changes update the specification version.
9. Approved changes create a Change Log entry.
10. Superseded requirements remain traceable through the Change Log or a resolved decision entry in this specification.

### A.2 AI development guardrails

- Read this specification before planning or implementing a feature.
- Cite the applicable requirement, invariant, security, and acceptance-criterion IDs in every implementation plan.
- Do not infer new product behavior from existing code alone.
- Existing code may be incomplete or inconsistent with this specification.
- Identify conflicts before implementation.
- If necessary behavior is unspecified, record it as an open decision.
- Do not silently resolve contradictions.
- Do not expand release scope without explicit approval.
- Preserve all applicable product invariants.
- Treat non-goals as active scope boundaries.
- After implementation, perform a requirement-by-requirement alignment audit.
- Report deliberate and accidental deviations honestly.
- Suggest specification changes when an approved product decision changes.
- Never edit the specification merely to make an implementation appear compliant.
- When code and specification disagree, report the disagreement before deciding which should change.
- A feature is not complete merely because the code executes; its acceptance criteria must be verified.
